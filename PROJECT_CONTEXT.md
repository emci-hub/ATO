# PROJECT_CONTEXT.md

## What ATO is
A self-based alternative to Costar-style astrology apps. Instead of generic daily content, it uses a multi-axis personality/behavior framework to generate accurate, personalized guidance. Goal: help users understand themselves and how they interact with others (e.g. why an extrovert might overwhelm an introvert), and nudge them toward growth and new experiences.

**Confirmed 16 axes** (`TRAIT_AXES` in `src/lib/traits.ts:15`): openness, conscientiousness, extraversion, agreeableness, steadiness, attachment_anxiety, attachment_avoidance, conflict_assertiveness, conflict_cooperativeness, autonomy, competence, relatedness, growth_mindset, locus_of_control, self_efficacy, playfulness.

- 2026-09-10: **Bug fix — ongoing-round "Next round" button mislabeled + generic error hid the real failure (`src/components/questions-fold.tsx`'s `OngoingRoundFold`).** Emci reported the CTA read "Next round" (should say "Submit," since it submits answers to load the next batch) and tapping it always showed "Could not load your next round. Try again." regardless of cause. Root cause investigated first: `load()` (mount-time fetch) and `start()` (button-tap compose+save) shared one boolean `error` state, so the UI rendered the identical load-failure copy no matter which action actually threw — undiagnosable from the user-facing text alone. Checked the live `ato` Supabase project directly (RPCs, RLS, bank-pool data) and found nothing obviously broken server-side, so the true underlying trigger is still unconfirmed; this fix targets the reporting gap, not a specific server bug. **Fixed:** heading renamed "Next round" → "Submit"; boolean `error` replaced with `errorKind: 'load' | 'start' | null` so each catch sets its own kind, the rendered message differs per kind ("Couldn't submit your answers." vs "Couldn't load your next round."), and the retry button now re-invokes whichever action actually failed instead of always calling `load()`. **Also added `Sentry.captureException(err)` alongside the existing `console.log` in both catch blocks** — flagged by emci that this app ships via OTA with no way to pull a real user's device console after the fact, so silent `console.log`-only failures are otherwise invisible. Matches the existing `src/lib/sentry.ts` pattern (`Sentry.init` in `_layout.tsx`, DSN-gated, `sendDefaultPii: false`); both reachable throw types (`PostgrestError`, `AiProviderError`) are real `Error` subclasses carrying no prompt/PII content. Review: PASS, no critical findings — noted but left out of scope (not requested): `pick()`/`reroll()` in the same component still only `console.log` their failures, and a now-redundant `disabled={loading || starting}` on the retry button. Gate: typecheck + lint (0 errors, 55 baseline warnings unchanged, none in the touched file). Not device-verified — if the underlying failure recurs, Sentry now captures it with a real stack instead of only a local console line. No schema/auth/dependency changes.

## Audit — Explore / Questions / token spend (2026-09-04, read-only)

### 1) Explore's trait/category data model

**16 trait axes** — `TRAIT_AXES` in `src/lib/traits.ts:16-33`, with `export type TraitAxis = (typeof TRAIT_AXES)[number]` at `traits.ts:35`. This is the single source of truth for axes. The list:
`openness, conscientiousness, extraversion, agreeableness, steadiness, attachment_anxiety, attachment_avoidance, conflict_assertiveness, conflict_cooperativeness, autonomy, competence, relatedness, growth_mindset, locus_of_control, self_efficacy, playfulness`
`EXTRA_AXES` (`traits.ts:37-45`) is the 7 non-Big-5 axes. Axis *definitions* are TS-only; axis *values* are per-axis numeric columns on the `me` row, read by `traitStateFromRow` (`traits.ts:215-243`) alongside jsonb `trait_sources` / `trait_touched_at`.

**Categories** — `CategoryId` union in `src/lib/categories.ts:18-29`, defs in `categories.ts:45-145`. The code currently ships **11** category ids, not 9:
`cat_steadiness, cat_openness, cat_drive, cat_agency, cat_social, cat_communication, cat_love, cat_independence, cat_levity, cat_structure, cat_resilience`
Levity is `categories.ts:118-126` (axes: `playfulness, conflict_assertiveness, conflict_cooperativeness`). `CATEGORY_COPY_REVIEWED = false` (`categories.ts:16`) — still unreviewed copy.
Categories are a **hybrid** source: the TS `CATEGORY_DEFS` const is the seed/fallback, and a live `category_defs` DB table can override it via `categoryDefFromRow` (`categories.ts:214-247`) + `setCategoryDefs`/`getCategoryDefs` (`categories.ts:152-165`). All category math reads `getCategoryDefs()`, never the const directly (see the comment at `categories.ts:147-151`).

### 2) Questions' data model — typed, not free-text

`src/lib/questions/types.ts` imports `TraitAxis` from `@/lib/traits` (`types.ts:2`) and types `axis: TraitAxis` on both `QuestionDraft` (`types.ts:13-17`) and `QuestionItemRow` (`types.ts:19-28`). So a question references the **same source of truth as Explore**, not a loose string name. There is no `category_id` on a question at all.

The one untyped entry point — model-generated JSON — is validated: `isAxis()` (`src/lib/questions/parse.ts:10-12`) checks `TRAIT_AXES.includes(value)`, and `parseQuestionDraft` (`parse.ts:23-33`) returns `null` for an unknown axis. Both `parseQuestionBatch` and `parseQuestionSweep` route through it. **No bypass found.** The static bank (`src/lib/questions/bank.ts:8-33` onward) uses axis literals that typecheck against the union.

### 3) Question engine coverage vs Explore

- **Explore's units:** 16 trait axes **and** 11 category ids.
- **Question engine's units:** 16 trait axes only. `src/lib/questions/*` never imports `CategoryId` or `categoryById`.

Diff:
- All 16 axes are covered — the bank has ≥1 item per axis, `parseQuestionSweep` caps at `TRAIT_AXES.length` (`parse.ts:78`), and `unfilledAxes`/`priorityAxes` drive axis rotation (`route.ts:186-192`). **No missing axis.**
- **All 11 categories have zero coverage** — the engine cannot target or generate toward a category. This is consistent with the architecture (questions write axes; categories are a read-side aggregation of axes), but it is **not documented anywhere as a deliberate non-goal**, so it reads as a gap. If "ask questions to complete category X" is ever wanted, it needs a new axis-mapping layer.
- Nothing the engine targets is unknown to Explore — the engine's set is a strict subset.

### Audit follow-up 2 — the three Explore counters + full app-wide token spend map (2026-09-04, read-only)

#### 1) The three counters — three *different* predicates over the same data

All three read the **report track only**; the `self_game` gut-call track never counts toward any of them (`trait-stability.ts:127-134`).

**a) "Full profile · X of 16 filled"** — [profile-fill-fold.tsx:38](src/components/profile-fill-fold.tsx:38), title built from `filledAxisLabel(tracks)`.
Chain: `filledAxisLabel` (`trait-stability.ts:239`) → `filledCount` (`:218`) → `filledAxes` (`:210`) → `isAxisFilled` (`:206`) = **`row.answerCount >= 1`**. That is the whole test — one answer on an axis fills it. At 16/16, `isProfileComplete` (`:233`) flips the title to the complete label instead.

**b) "How you're currently leaning · X of 16 settled"** — [explore.tsx:144](src/app/(tabs)/explore.tsx:144) (label) and `:173` (number), from `settledAxisLabel` / `settledCount`.
Chain: `settledCount` (`trait-stability.ts:156`) = `Math.round(settledScore)`; `settledScore` (`:148`) sums `effectiveStability(...)` across all 16 axes. `effectiveStability` (`:114`) returns **0 when `answerCount < STABILITY_FLOOR_N` (3)**, else `decayedStability` — full value for 60 idle days, then a 90-day half-life (`:102-112`).
So "settled" is a **rounded sum of fractional stabilities, not a count of axes**. It can move without any new answer (decay), and 16 axes each at 0.5 stability reads as "8 of 16 settled" while every one of them is filled. Filled and settled are documented as allowed to disagree (`trait-stability.ts:197-202`, `profile-fill-fold.tsx:30-32`).

**c) "Categories · X of 11 ready"** — [categories-fold.tsx:76](src/components/categories-fold.tsx:76), literally `${ready.length} of ${readings.length} ready` where `ready = readings.filter((row) => row.ready)` (`:40`).
`ready` comes from `readCategory` (`categories.ts:294-345`). **What "ready" means depends on the category's shape:**
- **bar** (8 of 11): `ready = stable.length >= def.minStable`, and `minStable` is **2** for every category — so a 3-axis bar is "ready" on 2 of its 3 axes.
- **map** (3 of 11 — `cat_love`, `cat_independence`, `cat_structure`): **both** named axes must independently clear the floor, else it does not render (`categories.ts:309-317`).
- "Clears the floor" = `reportStable` (`categories.ts:266-274`) → `effectiveStability(...) > 0` → **`answerCount >= 3` on that axis**, after decay.
- `texture` axes (only `cat_love` has them) are display-only and never affect `ready`.

**Net:** an axis needs **1** answer to count as filled, **3** to contribute to settled or to a category. A category needs 2 qualifying axes. These thresholds are independent, which is why the three numbers on one screen routinely disagree.
