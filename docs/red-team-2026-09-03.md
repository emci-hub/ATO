# Red-team pass — 2026-09-03

Adversarial read of the app as shipped on `master` at the time of writing. Deliberately
takes **new angles** rather than re-walking `docs/stage8-audit.md`: that pass was about
correctness of the check/trait pipeline. This one is about what a motivated attacker,
an annoyed user, and a bored user each do to the product.

Everything below is read from source. Nothing was executed against the live project, so
anything that depends on a runtime policy or a device render is tagged **(hypothesis)**.
Severity is product severity (what it costs us if it lands), not CVSS.

---

## 1. Security — exploits, abuse paths, data leaks

### S1. `login_email_for_identifier` is an anon-callable handle → email oracle
**Severity: High.** `supabase/migrations/auth_password_optional.sql:61` grants execute to
`anon`. Anyone with the publishable key (it ships in every bundle and in `landing/`) can
call the RPC with a handle and receive the account's login email.

*Impact.* Every public @handle becomes an email address. That is a deanonymisation
primitive on an invite-only app whose users did not consent to their handle being a
lookup key for their inbox, and it feeds credential stuffing and phishing against exactly
the small user set we most care about. This is also directly contrary to the privacy
copy's framing of the handle as the public surface.

*Fix.* Keep the RPC for the sign-in flow but stop it being a bulk oracle: require the
caller to already hold an unauthenticated session challenge, or rate-limit per IP at the
edge, or move the handle→email resolution inside an Edge Function that also does the
password attempt so the email never returns to the client. Cheapest correct version:
have the function return a boolean "this identifier exists, proceed" and let GoTrue take
the handle, not the email.

*Effort: M.*

### S2. Circle connection is consentless and mirrors both ways
**Severity: High.** `src/lib/circle.ts:63-101` resolves a handle then inserts
`{ user_id, peer_id }` with no request/accept step; the schema comment at
`src/lib/circle.ts:8` states the reverse row is mirrored on insert. `peer_checks`
(`supabase/migrations/peer_checks.sql:9-35`) is `security definer` and returns a peer's
Checks to anyone joined through `connections`.

*Impact.* Knowing a handle is sufficient to become someone's Circle. The attacker then
reads that person's daily Read/Do history through `peer_checks`, can open a DM thread,
and appears in their Circle list. Combined with S1 (handle is guessable/enumerable) and
S4 (handles are recyclable) this is the most serious abuse path in the app: it is
stalker-shaped, and the victim's only recourse is to notice and block after the fact.

*Fix.* Add a pending state to `connections` (`status: 'pending' | 'accepted'`) and gate
both `peer_checks` and thread creation on `accepted`. The scan gesture is still one tap
for the scanner; the scanned person gets one accept. **(hypothesis)** on the exact
mirror policy text — the base `connections` table and its RLS are not in
`supabase/migrations/`, so the mirroring is read from the client comment and
`peer_checks`, not from the policy itself.

*Effort: M.*

### S3. `ping: true` is an unmetered vendor call
**Severity: High.** `supabase/functions/ai-generate/index.ts:294` reads `ping` from the
caller's body; `:311` skips `claim_ai_call` entirely when it is set. `src/lib/ai/edge.ts:31`
sends the flag straight from the client.

*Impact.* Any authenticated user can post `{ ping: true }` in a loop and spend our vendor
budget without touching their 20/day. The prompt is fixed so the output is small, but
the request count is not bounded by anything. This is a billing DoS from inside the
invite list, and it also silently invalidates the "quota is claimed server-side"
invariant in `CLAUDE.md` — the invariant holds for content, not for probes.

*Fix.* Meter pings on a separate cheap counter (e.g. 10/hour/user) inside the Edge
Function, or make the probe not call a vendor at all — a key-presence check plus a cached
last-success timestamp answers the same question the provider dot asks.

*Effort: S.*

### S4. Unbounded prompt and unclamped temperature reach the vendor
**Severity: Medium.** `index.ts:295` takes the caller's `prompt` verbatim with no length
check; `:298` takes `temperature` as any number the caller sends. Only `maxOutputTokens`
is capped (`:303`).

*Impact.* Output is capped, input is not, and input is most of the cost on long-context
models. A user can post a multi-megabyte prompt and burn one quota unit for a very large
bill. `temperature: 9000` is a free way to make a vendor 400 on us (noise in error rates)
or to produce degenerate output attributed to Sage. It also turns the Edge Function into
a general-purpose proxy to our paid key: with an arbitrary prompt, a caller gets 20/day
of unrestricted model access under our account, not 20 ATO cards.

*Fix.* Clamp `temperature` to `[0, 1.2]` and reject prompts over ~8k characters. If we
want the proxy to only ever produce ATO content, build the prompt server-side from a
`callType` + a small structured payload instead of accepting free text.

*Effort: S.*

### S5. The quota is claimed before the vendor answers, and the client fallback double-claims
**Severity: Medium.** `index.ts:311-318` claims, then calls the vendor at `:323`.
`src/lib/ai/generate.ts:74-79` catches a Gemini failure and re-enters `completeFor('deepseek', …)`,
which is a second Edge Function call and therefore a second claim.

*Impact.* A vendor outage costs the user their day: they lose a call for a card they never
saw, and a Gemini failure costs two of twenty for one card. From the user's side this
reads as the app eating their allowance, which is the single most trust-corrosive bug a
metered product can have.

*Fix.* Refund on vendor error (a `release_ai_call` companion RPC), or claim after a
successful vendor response and accept the small race. For the fallback specifically, pass
the already-claimed token through so the retry does not re-claim.

*Effort: M.*

### S6. Every AI surface drains one shared bucket, and `by_type` is always `'sage'`
**Severity: Medium.** `index.ts:307` defaults `callType` to `'sage'` and only recognises
`'explore'`. `src/lib/ai/edge.ts:25-32` never sends `callType` at all — the field is not in
the body. `src/lib/voice/quota-server.ts:32` still takes a `callType` parameter, but that
path is a no-op for edge providers.

*Impact.* Questions, Story, Title, Explore and Insight all draw down the same 20/day, and
the `ai_usage.by_type` breakdown the wave17/20/22 migrations were written around is a
constant. Two consequences: we cannot see what users actually spend on, and the "spend"
affordances in the UI (Insight spend, Story, Title) are quietly competing with the
product's core loop. A user who explores for five minutes has no card budget left.

*Fix.* Send `callType` from `edge.ts` and widen the server-side allowlist to the real set.
Then decide the lane policy deliberately: card generation should almost certainly have a
reserved floor that Explore cannot eat.

*Effort: S* for the plumbing, *M* for the lane policy.

### S7. Three surfaces auto-generate a card on mount, three attempts each
**Severity: Medium.** `src/app/(tabs)/index.tsx:241-266` fires `routeVoiceCard` from a
`useEffect` on mount whenever today has no card. `GENERATED_MAX_ATTEMPTS = 3`
(`src/lib/voice/config.ts:11`) and the router loops that many times
(`src/lib/voice/router.ts:282`) because filtered drafts are retried. Dawn and the missed-check
card do the same thing.

*Impact.* Opening the app can spend up to three quota units before the user has tapped
anything, and the effect's dependency array includes `checks` and `tracks`, so a state
change that reruns it spends again. Users will hit "That's all for today" without ever
having asked for anything. This combines badly with S5: a filtered draft and a vendor
error both cost the same as a delivered card.

*Fix.* Only the Dawn flow should generate. Home should render what exists and offer a
button. Cap retries at 2 and make the third attempt fall back to the written bank rather
than another paid call.

*Effort: M.*

### S8. Crisis-flagged user text is persisted
**Severity: Medium.** `src/app/(tabs)/sage.tsx:341` calls `persistAndSwap(localUserId, 'user', trimmed)`
before the router runs, so the user's message is written to `sage_messages` regardless of
outcome. The comment at `:376-378` correctly says the crisis *card* is not persisted — but
the message that triggered it already is.

*Impact.* The most sensitive sentence a user will ever type into this app is stored in a
table with ordinary retention, and the privacy copy implies crisis turns are not kept.
That is both a promise we are breaking and the row we least want in a breach or a
subpoena.

*Fix.* Persist the user line *after* the router returns, and skip the write when
`result.kind === 'crisis'`. The reportable-id ordering that motivated the early write can
be preserved with an optimistic local id swapped on success.

*Effort: S.*

### S9. Free-text columns are unbounded
**Severity: Medium.** `supabase/migrations/stage7_chat_report.sql:127` (`messages.text`),
`:248` (`sage_messages.text`) and `:269` (`reports.reason`) all check only that the value is
non-blank. `text` in Postgres is unbounded.

*Impact.* One authenticated user can write arbitrarily large rows into shared tables. A DM
of a few hundred MB is a storage cost, a client OOM for the recipient, and a way to make
a thread permanently un-openable — a targeted denial of service against one person, which
is worse than a generic one because it is aimed. Reports have no rate limit either, so
mass-reporting an account is free.

*Fix.* `check (char_length(text) <= 4000)` on messages and sage messages, `<= 2000` on
report reasons, plus a per-user insert rate limit on `reports`.

*Effort: S.*

### S10. `handleFromScannedText` extracts a handle from any pasted text
**Severity: Medium.** `src/lib/share-codec.ts:15` is `text.match(/@([a-z0-9]{1,20})/i)` — the
first `@`-token anywhere in the input wins.

*Impact.* Paste an email address and you connect to `@gmail`. Paste a tweet and you
connect to whoever it mentions. Because the connection is consentless (S2) and mirrored,
a mis-paste silently gives a stranger read access to your Checks. There is no confirm
step between parse and insert.

*Fix.* Require the ATO link shape or a leading `@` at the start of the trimmed input, and
show a confirmation with the resolved name/handle before writing the row. Squatting
`@gmail`, `@icloud`, `@outlook` is a five-minute mitigation worth doing today.

*Effort: S.*

### S11. Handle recycling enables impersonation of old QR codes and links
**Severity: Medium.** `complete_signup` re-saves `handle` on the existing row
(`supabase/migrations/stage9_intake_core.sql:108`, same shape at
`founder_access_requests.sql:179`) and nothing reserves a released handle.

*Impact.* If a user changes handle (or an account is deleted), the freed handle can be
taken by someone else, and every printed QR, share card, and link that pointed at the old
owner now resolves to the new one. Combined with the consentless connect, the new owner
inherits an audience that believes they are talking to the old one. **(hypothesis)** on
whether the product currently exposes a handle change at all — I did not find a settings
affordance for it, so the exposure may be limited to deleted accounts today.

*Fix.* Tombstone released handles for a long window (a `retired_handles` table checked in
`complete_signup`), and never re-issue a handle that has ever had connections.

*Effort: S.*

### S12. The landing page is an email-existence oracle and an unrate-limited insert
**Severity: Low.** `landing/index.html:136` branches on a 409 to say "That email is already
on the list", which is exactly the unique-index violation from
`founder_access_requests.sql:307`. `access_requests_insert_public` (`:316-318`) grants
insert to `anon`.

*Impact.* Anyone can test whether a given address requested access — a small privacy leak
about a small, identifiable population. And anyone can fill `access_requests` with junk,
which is our own invite-review queue, i.e. a direct attack on the one manual process the
launch depends on.

*Fix.* Return the same "thanks, we'll be in touch" for both cases. Put a captcha or an
edge rate-limit in front of the insert.

*Effort: S.*

### S13. Client-writable trait, title and story columns
**Severity: Low, rising to Medium at launch.** The `me` update policy is `auth.uid() = id`,
and `trait_tracks`, `sage_title` and `sage_story` are ordinary columns on rows the user
owns. `CLAUDE.md` documents the intended path (`mergeTraitWrite` → `updateTraits`) but
that is a client-side convention, not an enforced one.

*Impact.* A user with the publishable key and their own JWT can set their own traits to
anything, which makes the "settled" state and the Legends match meaningless for that
account. More concretely: `sage_title` is shown to consented peers, so a user can write
arbitrary text into a field that renders in someone else's app — a small content-injection
surface for harassment. Self-modification of one's own traits is mostly self-harm; the
peer-visible fields are not.

*Fix.* Move the peer-visible fields (`sage_title`, and `sage_story` if it ever becomes
shared) behind a security-definer RPC that validates length and applies the same jargon
filter the generator uses. Traits can stay client-writable while invite-only, but the
column trigger pattern already used for `is_root` (`wave34_root_is_column.sql`) is the
model to copy before launch.

*Effort: M.*

### S14. `ai_provider_log` rejects `deepseek`
**Severity: Low.** `supabase/migrations/ai_provider_layer.sql:8` constrains
`provider in ('gemini','nvidia','perplexity','claude','grok')`. `src/lib/ai/usage.ts:35`
inserts the provider name, and `generate.ts:76` uses `'deepseek'` as the fallback.

*Impact.* Every fallback call fails its log insert and is swallowed by the `console.log` at
`usage.ts:36`. Our own provider counts under-report exactly the calls we most want to
count — the ones where the primary vendor failed. The `/ai-lab` numbers are wrong and we
would not know.

*Fix.* One-line migration adding `'deepseek'` to the check.

*Effort: S.*

### S15. `set_going` / `night_snapshot` take arbitrary show ids
**Severity: Low.** `supabase/migrations/wave2_going_colors.sql:159` and `:90` are granted to
`authenticated` and take `p_show_id text` with no referential check.

*Impact.* A caller can mark themselves going to ids that do not exist (junk rows), and can
call `night_snapshot` on any id to read who is going. Around is small and the data is
opt-in, but "who is out tonight" plus a face is the highest-stakes small dataset we hold.
**(hypothesis)** on what `night_snapshot` actually returns per row — I read the grant and
signature, not the full body.

*Fix.* Foreign-key the show id, and scope `night_snapshot` to shows in the caller's city.

*Effort: S.*

### S16. The provider switcher is reachable by every user
**Severity: Low.** `src/app/ai-lab.tsx` has no `PRE_LAUNCH_DEV` or root guard — the header
comment says it opens on five taps of the Build line, and `setProviderOverride` is
per-device AsyncStorage.

*Impact.* Any user who finds the tap can point their calls at Claude or Grok. If those
keys are set as Supabase secrets, that is our most expensive model serving one curious
user's whole quota. It also makes support impossible: two users on the same build get
different Sage voices with no server-side record of why.

*Fix.* Gate the screen on `PRE_LAUNCH_DEV` like `dev-lab`, or on `me.is_root`.

*Effort: S.*

### S17. The widget puts the day's Read on the lock screen
**Severity: Low.** `targets/widget/widgets.swift:53,61` render `entry.read` and
`entry.doText` directly.

*Impact.* The Read is personal, sometimes pointedly so. On the lock screen it is visible to
anyone who picks up the phone. We never asked the user whether that is okay.

*Fix.* Offer a redacted widget mode (title only, "Open ATO") and make it the default.

*Effort: S.*

### S18. The base schema is not in the repo
**Severity: Medium (process).** `supabase/migrations/` starts at `stage*` and assumes `me`,
`checks`, `connections`, `crisis_flags` and `public_profile` already exist with their RLS.

*Impact.* We cannot review the policies that matter most — the ones on the tables holding
everything — and we cannot rebuild the project from source. Every RLS finding in this
document is partly **(hypothesis)** for that reason. This is also the single biggest
obstacle to any future security review.

*Fix.* Dump the current schema and policies into a `0000_baseline.sql` and commit it.

*Effort: S.*

## 2. Graphics / Visual

### G1. Quest mode forces every heading gold, ignoring `themeColor`
**Severity: Medium.** `src/components/themed-text.tsx:35`:
`color: theme.id === 'quest' ? theme.emphasis : theme[themeColor ?? 'text']`.

*Impact.* A caller that explicitly asks for `themeColor="textSecondary"` on a heading gets
gold in Quest mode. Secondary headings, section labels and de-emphasised titles all render
at full emphasis, so the visual hierarchy collapses into a wall of gold in exactly the
mode that is meant to feel the most designed.

*Fix.* `color: theme.id === 'quest' && !themeColor ? theme.emphasis : theme[themeColor ?? 'text']`.

*Effort: S.*

### G2. Expo template assets still ship
**Severity: Medium.** `src/components/animated-icon.tsx:36,102,107` load `expo-logo.png` and
`logo-glow.png`; `:143` hardcodes `#208AEF`. `app.json:144,154` set the same blue for the
notification icon and splash. `targets/widget/expo-target.config.js:18` sets it as the
widget accent.

*Impact.* The splash, the push icon and the widget accent are Expo's brand, not ours. First
launch — the highest-signal moment in the product — shows a template. For an app whose
entire pitch is that it was made for you specifically, this reads as unfinished.

*Fix.* Replace the three assets and the accent with ATO's mark and palette before any
build that leaves the invite list.

*Effort: S* once the assets exist.

### G3. `fontFamily: 'monospace'` is not a valid iOS family
**Severity: Low.** `src/components/share-poster.tsx:116`.

*Impact.* On iOS this silently falls back to the system font, so the poster's intended
monospace line renders as body text. The poster is our only outbound artefact — it is what
non-users see — and it is the one place a font bug is public. **(hypothesis)** on the exact
fallback: not device-verified.

*Fix.* `Platform.select({ ios: 'Menlo', android: 'monospace' })`, or use the `Fonts.mono`
token that `themed-text.tsx:42` already resolves.

*Effort: S.*

### G4. Two button systems, one of them theme-blind
**Severity: Medium.** 24 files reference hardcoded `#3c87f7`, `#E5484D` or
`rgba(0,0,0,0.04)` (scan sheet, report sheet, delete-account sheet, consent card, auth
screens, chat, Circle, Sage, You, onboarding, Dawn) while `ThemedPressable` and
`theme.accentFill` exist.

*Impact.* On the dark appearance modes, `rgba(0,0,0,0.04)` surfaces are invisible — a
control that exists but cannot be seen. The blue and red do not shift with the five
appearance modes, so a user in Neon or Quest gets stock iOS blue buttons inside a themed
screen. Five appearance modes is a headline feature; this is the thing that makes it feel
half-applied.

*Fix.* Sweep the 24 files onto the theme tokens. This is mechanical and high-yield.
A `check:` script asserting no raw hex under `src/components` would keep it from
returning.

*Effort: M.*

### G5. `BottomTabInset` is a guess that does not match the real bar
**Severity: Low.** `src/constants/theme.ts:63` hardcodes `ios: 50, android: 80`, while the
actual bar height is `Math.max(insets.bottom, Spacing.two)` plus content
(`src/components/app-tabs.tsx:63`).

*Impact.* Ten screens pad their scroll views by a constant that is right on no device.
Where it under-shoots, the last row sits under the tab bar; where it over-shoots, there is
dead space. On a device with a home indicator the two disagree by roughly the indicator
height. **(hypothesis)** on the direction and size of the error per device — this needs a
render to confirm.

*Fix.* Measure the bar with `onLayout` into a context, or compute the same expression the
bar uses instead of a constant.

*Effort: M.*

### G6. `NAV_PIXEL_HEADER_INSET` is applied on 7 screens but not on Circle or Explore
**Severity: Low.** The inset is imported in `intake-sweep`, `nav-pixel`, `around`, `index`,
`legends`, `sage`, `you` — Circle and Explore are absent.

*Impact.* The nav pixel overlaps the header on the two screens that do not compensate.
**(hypothesis)** — this is inferred from the import list, not from a render.

*Fix.* Apply the inset on both screens, or move it into the shared screen scaffold so it
cannot be forgotten.

*Effort: S.*

## 3. UI — layout, responsiveness, accessibility

### U1. The nav editor's instructions contradict the cap it enforces
**Severity: Medium.** `src/components/nav-edit-overlay.tsx:105` reads "2 slots — Home and
Sage always stay, plus two more", while `MAIN_BAR_CAP = 3`
(`src/lib/nav/nav-order.ts:90`) is what `:51` and `:172` actually enforce.

*Impact.* The copy says two numbers, neither of which is three. Users will try to add a
fourth tab and find the button disabled with no explanation. Personalised navigation is a
differentiator; a broken explanation of it is worse than no explanation.

*Fix.* Derive the sentence from `MAIN_BAR_CAP` so it cannot drift again.

*Effort: S.*

### U2. Crisis numbers are not tappable
**Severity: High for the moment it matters.** `src/components/crisis-card.tsx:41-48` renders
each action as `<View>` with an icon and a `ThemedText` label — "Call 988", "Text 988"
(`src/lib/crisis/copy.ts:40-41,46-47`). There is no `Pressable`, no `Linking`, no `tel:` or
`sms:`.

*Impact.* We detect a crisis, we show the right number, and then we ask a person in the
worst state of their life to memorise three digits and switch apps. Every competitor makes
this one tap. This is the highest-stakes interaction in the product and it is inert.

*Fix.* Wrap each row in a `Pressable` calling `Linking.openURL('tel:988')` /
`sms:988`. Keep the text visible for the case where the URL fails.

*Effort: S.*

### U3. The Explore fold labelled "Today's Read" contains the title card
**Severity: Low.** `src/app/(tabs)/explore.tsx:138`.

*Impact.* The user taps a fold expecting today's Read and gets something else. Small, but
it is the kind of mislabel that makes people stop trusting the navigation.

*Fix.* Rename the fold to what it holds.

*Effort: S.*

### U4. Onboarding promises nine taps, the sweep is eight
**Severity: Low.** `src/app/onboarding.tsx:484` says "then nine taps";
`src/components/core-intake-sweep.tsx:15` is `CORE_INTAKE_SWEEP_TITLE = 'Eight quick taps'`.

*Impact.* The first promise the app makes is off by one, and the correction arrives one
screen later. It is a trivial bug that signals carelessness at the exact moment we are
asking for trust.

*Fix.* Import the constant into the onboarding copy.

*Effort: S.*

### U5. "You showed up 1."
**Severity: Low.** `src/app/week.tsx:61` has an explicit singular branch that produces the
same broken sentence as the plural branch.

*Impact.* Somebody wrote a conditional specifically to handle the singular and then put
the same ungrammatical string in both arms. Every user sees this on their first week.

*Fix.* "You showed up once." / "You showed up N times."

*Effort: S.*

### U6. Tab triggers announce as generic buttons
**Severity: Medium (accessibility).** `src/components/app-tabs.tsx:85,131` use
`accessibilityRole="button"`.

*Impact.* VoiceOver announces "More, button" instead of a tab with a position and a
selected state. A screen-reader user cannot tell which tab is active or how many there
are. Since the tab bar is custom (not the platform one), nothing else supplies this.

*Fix.* `accessibilityRole="tab"` on the triggers, `accessibilityState={{ selected }}`, and
`accessibilityRole="tablist"` on the bar.

*Effort: S.*

### U7. `Vibration.vibrate(10)` instead of a haptic
**Severity: Low.** `src/components/reveal-card.tsx:2,28`.

*Impact.* On iOS `Vibration` triggers the full vibration motor, not the Taptic Engine, and
short durations are ignored — so the reveal either buzzes crudely or does nothing. The
reveal is the app's one celebratory moment and its feedback is the wrong instrument.
**(hypothesis)** on the exact iOS behaviour without a device.

*Fix.* `expo-haptics` with `impactAsync(Light)`. It is not currently a dependency, so this
needs emci's ok per `CLAUDE.md`.

*Effort: S.*

### U8. The You tab is a wall
**Severity: Medium.** `src/app/(tabs)/you.tsx` renders on the order of 25 stacked folds and
sections in one scroll.

*Impact.* Everything is technically reachable and nothing is findable. The tab holds the
profile, the traits, the settings, the legal links, the subscription rows and the dev
tools with no grouping strong enough to skim. New users will not discover the good parts
(Full Profile, Legends) and returning users will not find settings.

*Fix.* Split into You (identity + profile) and Settings (everything administrative), or
introduce a two-level structure with a small index at the top.

*Effort: L.*

## 4. UX — confusing flows, friction, drop-off

### X1. Home generates a card while telling the user nothing is being made
**Severity: High.** `src/app/(tabs)/index.tsx:382` renders "Open Dawn when you're ready.
Nothing is made up in the meantime." The effect at `:241-266` on the same screen calls
`routeVoiceCard` on mount.

*Impact.* The copy is a promise about restraint — it is the product's whole posture — and
the screen breaks it in the same render pass. When the user then opens Dawn, the card is
already made, so the ritual we built the app around is a reveal of something that happened
without them. If they ever notice the quota moving while the screen says nothing is
happening, the promise reads as a lie rather than a bug.

*Fix.* Make Home render-only. Generation belongs to Dawn. (This is also the fix for S7.)

*Effort: M.*

### X2. Filtered drafts spend the user's day
**Severity: High.** The router retries up to `GENERATED_MAX_ATTEMPTS` (3) when
`src/lib/voice/filters.ts` rejects a draft, and each attempt is a claimed call.

*Impact.* Our quality filter is billed to the user. A day where the model happens to write
three cuts in a row costs three units and delivers nothing, and the user sees "That's all
for today" having received one card or none. The user cannot distinguish "I used my day"
from "the app wasted my day", so they assume the latter.

*Fix.* Claim once per delivered card, not per attempt — the retry loop should reuse the
claim. Failing that, fall back to the written bank on attempt 3 instead of spending a
third call.

*Effort: M.*

### X3. The consent modal blocks the Sage tab
**Severity: Medium.** `src/app/(tabs)/sage.tsx:630` renders the consent card whenever
`consent === 'pending'`.

*Impact.* A user who wants to look at Sage before deciding cannot. The modal asks for a
decision about a feature they have not seen, which is the worst possible order for an
informed choice — and the likeliest outcome is a reflexive "no" that permanently degrades
the product for that account.

*Fix.* Let the tab render in a read-only state with an inline consent prompt at the
composer. Ask at the moment of first send.

*Effort: M.*

### X4. Banked cards use streak language the product forbids

### F2. The eight-ball is the only toy, and it is off to the side

*Impact.* We built one delightful thing and hid it. The rest of the app is competent and

*Fix.* Give the eight-ball a home (a shake gesture anywhere in Sage), and budget one small

## 6. Missing opportunities

### O1. `explore_reactions` is written and never read
Only `src/lib/explore/store.ts` touches it. We are collecting per-item reactions and
surfacing nothing. That data is a ready-made "what you keep coming back to" fold on You,
and a ranking signal for Explore itself. **Effort: M.**

### O2. `crisis_flags` and `ai_provider_log` are write-only
`crisis_flags` is the signal that a user is struggling and nothing acts on it — not even a
gentle "yesterday looked heavy" adjustment to the next Read (which the router already has
`crisisYesterday` plumbed for at `index.tsx:250`). `ai_provider_log` (see S14) is broken
for the fallback case and unread otherwise. **Effort: M**, and the crisis one needs care
and emci's read on the copy.

### O3. No Circle request/accept, so no Circle social loop
Beyond the security case (S2), the missing accept step is also a missing product: there is
no notification, no "X added you", no reciprocity moment. Every competitor's growth comes
from that loop. **Effort: M.**

### O4. Nothing surfaces trait *movement*
`trait_tracks` holds EWMA history and `divergingAxesFromTracks` already computes
divergence for the prompt (`sage.tsx:369`). The user never sees it. "You've moved on
conscientiousness this month" is the single most compelling thing a trait product can say,
and we compute it and throw it away. **Effort: M.**

### O5. No share of anything but the poster
The poster (`share-poster.tsx`) is the only outbound artefact, and it has a font bug (G3).
Legends cards, milestone badges and week summaries are all more shareable and all already
rendered. **Effort: M.**

### O6. No streak-free consistency view worth opening
`week.tsx` is a count. Given the no-streak principle (X4), the opportunity is a *shape* —
a small honest visual of the last N days that does not punish gaps. This is the thing the
principle should buy us and we have not built it. **Effort: M.**

## 7. Additional insights

### A1. Docs assert the old key model
`docs/ME.md` and `docs/BUSINESS.md` still describe Gemini/NVIDIA/Perplexity keys as
client-side. That is now false — this branch removes the last of the client key plumbing —
and `BUSINESS.md` is the document most likely to be quoted at an investor or a lawyer.
Fixed for `MAP.md`, `GOTCHAS.md`, `NOW.md` and `DATA_AI_MAP.md` in this branch; ME.md and
BUSINESS.md still need emci's pass because the claims are commercial, not technical.

### A2. `privacy.md` overstates and understates
`src/app/legal/privacy.md:72` promises a discoverability control the app does not appear to
expose; the document does not mention the push token; the "only facts stored" framing does
not match `sage_messages` retention (and see S8). A privacy policy that describes a
different app than the one shipped is a legal exposure, not a docs bug. **Effort: M**,
needs emci.

### A3. The gate had a live check in it
`legends-live` was in the gate and would fail on any machine without `.env.local`, so
`npm run check:ota-gate` was red for reasons unrelated to the code being shipped — which
is precisely how a gate stops being trusted. Fixed on this branch
(`scripts/ota-gate.ts:40`).

### A4. `NOW.md` claimed 16 type errors that no longer exist
The gate now runs typecheck and lint as preflight and both are clean. Stale "known broken"
notes are worse than no notes: they train the reader to ignore the file.

### A5. Live checks spend real quota
`card-live` (3), `talk-live` (2) and `style-live` (12) together spend 17 of the dev-test
user's 20/day. Running the live suite twice in a day is impossible. Documented in
`GOTCHAS.md` on this branch; worth a dedicated dev quota lane later.

## Quickest wins

Ranked by (impact ÷ effort). All are one-file or one-line changes.

   one-line edits; the largest single improvement to how the app feels.

   `Pressable` each.
3. **Clamp temperature and prompt length in `ai-generate`** (S4) — two guards, closes the
   open-proxy shape.
4. **Meter or remove the `ping` path** (S3) — closes the unmetered vendor call.
5. **Stop persisting crisis-flagged messages** (S8) — move one line below the router call.
6. **Fix the Quest heading colour override** (G1) — one condition.
7. **Add `deepseek` to the `ai_provider_log` check** (S14) — one migration line; makes our

## Biggest risks

1. **Consentless Circle + handle→email oracle + loose handle parsing** (S2, S1, S10, S11).
   These compose into a stalking primitive: enumerate a handle, get an email, connect
   without consent, read their daily history. Any one alone is a bug; together they are the
   thing that ends an invite-only app's reputation. Fix S2 first — the accept step breaks
   the chain.
2. **The Edge Function is an open proxy to our paid key** (S3, S4, S5, S7). Unmetered ping,
   unbounded prompt, unclamped temperature, claim-before-response, and three auto-generating
   surfaces. The billing exposure is real and the quota unfairness is what users will
   actually complain about.
3. **Crisis handling is inert and leaky** (U2, S8). We detect correctly and then fail at
   both ends: the number cannot be tapped, and the message is stored. This is the one area
   where a bug is a safety issue rather than a product issue.
4. **The base schema is unreviewable** (S18). Every RLS conclusion here is provisional
   because the policies on `me`, `checks` and `connections` are not in the repo.
5. **Legal copy describes a different app** (A2, A1). `privacy.md` promises a control that
   does not exist and omits data we collect.

## Best opportunities

1. **Trait movement as the headline feature** (O4). We already compute divergence for the
   prompt and show the user nothing. "Here is how you have changed" is the payoff the whole
   16-axis backbone was built for, and it is the one thing a daily-card competitor cannot
   copy without our history.
2. **Circle as an actual loop** (O3). Adding accept fixes the security hole *and* creates
   the notification moment that every social product grows on. Rare case where the safe
   design is also the growth design.
3. **Legends at scale** (F3). It is the most shareable surface and it is content-limited,
   not engineering-limited. Twenty figures turns a novelty into the reason people post
   about the app.
4. **Reactions as a personal map** (O1). Already collected, never shown; a "what you keep
   coming back to" fold is nearly free.
5. **A consistency view that honours the no-streak principle** (O6). We took the harder,
   kinder position on streaks and then built nothing that shows why it is better. This is
   where the principle becomes a feature instead of an absence.
