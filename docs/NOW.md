## Crisis detection — final architecture (revised — reverted to keyword-only)
**Current:** static keyword/phrase-list detection only, checked against the user's message before it reaches the router — matching the plan's original spec. No AI classifier call.
**Prior approach (superseded):** AI-judged (separate lightweight Gemini classification call) with keyword-list fallback if the classifier failed/timed out. Live-verified working (7/7 checks) as of Stage 5, but reverted after measuring real cost: the classifier call burned 487–561 invisible thinking tokens on **every single Talk message**, before the main reply even generated — real recurring token cost and latency for a catch-rate benefit judged not worth it once the actual numbers were known. Reverting returns to the plan's original design ("static keyword/phrase list... No sentiment model in v1 — keyword match is auditable and fails safe"), not a new invention.
**Unchanged by this reversal:** no confirmation gate before showing the card — shows automatically, one-tap dismiss, no lockout. Persistent subtle support button in Talk UI regardless of detection. Static resource card, logging (flag + timestamp only), router short-circuit (no model call on a flagged message) — all identical to before, only the trigger mechanism changed. Legal disclaimer draft in crisis-disclaimer.md — still needs a lawyer's pass before real users.

Same character as Home's pixel, marked with a subtle glow/shine tell so it reads as "the version you're working toward," not current-you. See ME.md's "Sage/Pixel relationship" note for the full reasoning — this is a real redefinition of what Sage represents (aspirational-you, not a separate coach character), not just an icon swap.
- **Growth tiers — dual-axis design (BUILT):** two separate signals, deliberately kept distinct rather than blended into one score, per standard progression-design practice (vertical "showed up" axis + horizontal "known deeply" axis, shown as separate visual channels so each stays legible on its own):
  - **Presence axis** (drives glow intensity on Sage's pixel/header avatar): tier 0 `check_count < 3` (matches Home's plain look — NO glow) → tier 1 `≥ 3` (subtle glow) → tier 2 `≥ 7` (existing plan unlock threshold, glow intensifies) → tier 3 `≥ 21` (~3 weeks, most distinct).
  - **Depth axis** (drives a separate small 4-point sparkle/spark marker, a distinct shape from the glow so the two signals don't blend): tier 0 = 0 facts known → tier 1 = a few facts known (~3+) → tier 2 = meaningfully known (~8+).
  - Both derived **live** from counts (`checks` table length for presence, `me.facts` array length for depth) — no cached tier to reconcile, no continuous scoring to maintain. **Hard rule: tiers only ever go up, never down** — monotonic by construction since each axis is a pure function of a monotonically-increasing count.
  - **Storage added (small migration):** `me.facts` (jsonb array of strings — the depth-axis input, populated by Stage 7's "Teach Sage this" via the new `addFact` helper) and `me.milestones_celebrated` (jsonb map of threshold → ISO timestamp, so each milestone fires exactly once). Both have `[]`/`{}` defaults; existing rows unaffected.
  - **Milestone celebration (BUILT):** a one-time louder burst on the header avatar (bigger scale pulse + both hands up in peace, via the existing Reanimated/override infrastructure — no new animation machinery) at the same presence-tier thresholds (7, 21 days), gated by `milestones_celebrated` so it fires exactly once per user per threshold. Layered on top of the daily gesture payoff, not replacing it.
  - Applied to: **header avatar** (live face + glow/sparkle + celebration) and the **web Sage tab icon** (static face + glow/sparkle). Native tab keeps the template-tinted silhouette — a native tab bar can't render colored glow/sparkle (template tint is monochrome), so the axes live on the color-capable surfaces.
  - **Neon glow redesign (2026-08):** the presence glow is now a layered neon treatment in the character's OWN color — a bright near-white core at the character's edge + the accent color as softer halos further out (2-3 concentric layers, decreasing opacity, increasing scale; tier 1 = core, tier 2 = +halo, tier 3 = +outer). No real blur — solid tinted ellipses, so it's cheap and animates via opacity/scale (not blur radius). Hue comes from `resolveFacePalette(recipe.palette, show_up)` so the glow matches the character underneath. The depth sparkle stays a sharp small white 4-point star (no blur), deliberately distinct from the soft glow. Halo saturation is capped ~92 so already-vivid bases (Kenney blue/pink) don't wash to near-white pastel.
  - **Color system — Ink/Paper/Steel/Bloom divergence (documented, intentional):** the plan named four fixed colors, but what actually shipped is a **hash-of-`show_up`-to-hue accent** — `hsl(hashString(show_up) % 360, 65%, 50%)`, so 360 possible hues instead of 4. This is the real, intentional implementation, not a bug to reconcile: a per-user hue from their own words is arguably a better fit for "your own color" than four fixed options. The plan's four named colors were never materialized as constants.
  - **Glow hue vs sprite color — two intentionally separate systems:** the glow hue (from `show_up` via the hash accent) and the body sprite's Kenney-variant color (nearest-variant asset selection) are deliberately NOT meant to match. A character can have a blue Kenney body and a different-hue glow. Do NOT "fix" these into false consistency later — they serve different purposes (sprite = the character's physical look; glow = the aspirational signal derived from the user's own words).
  - `scripts/growth-check.ts` (`npm run check:growth`, 10/10) verifies tier boundaries, monotonicity, milestone once-only gating, and the neon glow color derivation + halo saturation clamp.

## Backlog addition — Kenney import pipeline (queued after Stage 6 close)
Plan to build a generalized, family-agnostic Kenney asset pipeline rather than a one-off Pixel fix, since more Kenney packs are coming:
- One-time asset-prep script: re-export any pack's native PNGs to one fixed target resolution (derived from the largest actual render context — e.g. the Share poster — not picked arbitrarily), so the app never touches a pack's raw native size directly.
- Per-family manifest (`assets/kenney/<family>/manifest.ts`): declares part slots, anchor offsets ("skeleton," measured like Stage 3's original anchors), color variants, discrete swap-states (blink/gesture/mouth) — different packs can have different skeletons, just a different manifest.
- One generic renderer component reading `recipe + manifest`, family-agnostic — adding a new pack later means "manifest + prep script run," not new rendering code.
- One generic animation layer: discrete state swaps per the manifest's declared states, plus procedural transforms (breathe/bob/tilt/squash) via Reanimated applied to the composed group — doesn't care which family is active.
- `docs/KENNEY_IMPORT.md` — repeatable checklist capturing the above so future packs don't require re-deriving the approach.
- Also: confirm whether current Pixel rendering is tinting a neutral asset at runtime (likely root cause of the "flat/plain" look) vs. selecting pre-colored files — check this before assuming a resolution-only fix is needed.
- Shape Characters pack (`kenney_shape-characters.zip`) is the first candidate to migrate through this pipeline once it's built.
